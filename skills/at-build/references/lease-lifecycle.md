# Builder-pool wave protocol: the per-task lease loop

Phase 2 runs the builder pool (the `wave-orchestration` skill, "Builder-pool wave protocol", carries the full mechanics). The single-writer rule is retired: every implementation task, including lead-authored ones, is assigned from `ops/roster.toml`, built under a per-task lease in an isolated worktree, and merged only after cross-review by a pinned non-author reviewer. Safety is leases + worktree isolation + cross-review, not write-restriction.

Per task, with the helper sourced from the preflight:

1. `lease_create <task> <role>` → `lease_dispatch <task> <prompt>`: the builder is resolved via `resolve_role`, context is injected (task rows, the `ops/CONTRACTS.md` slice, the roster entry), and the builder runs confined in its worktree and commits nothing.
2. Wait with `lease_wait [task...] [--budget <s>]`, the only waiting primitive. Builders run detached in their own session and process group, so they outlive the lead's turn and tool calls. Each call blocks until a watched lease leaves `building` or its budget runs out (rc 75, `still building: …`), and never past the lead's `wait_budget_s` from the CLI registry; pass that limit to the call explicitly (the lead reference says how). While it waits, it collects a finished builder through `lease_collect` and prints `<task> <state>`. **Done condition:** call `lease_wait` in bounded slices, handling each lease it reports, until no dispatched lease is `building` (no `still building:` line). Each repeat call names only the leases on that `still building:` line, or names none to watch every building lease: a named lease that already left `building` returns the call at once. rc 75 means the budget ran out with builders still running: call it again. rc 80 means a building row could not be verified: that ends the loop, so stop and read the message. rc 44 is an integrity escalation (`wave-orchestration`, integrity escalations). Never poll in a tight loop; never wrap it in `sleep` loops of your own. A lead that ends its turn leaves the builders running; on resume, `lease_heartbeat_check` collects what finished while no lead was watching (`reason=lead-exit`, requeue budget untouched) and adopts what still runs. On collect (state → review; the row's `output_file` holds the builder's output), a typed final report ending in `Status: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT` is required: DONE and DONE_WITH_CONCERNS route to review; BLOCKED and NEEDS_CONTEXT route to escalated; a clean exit with no Status line is "report missing" (rc 80), so re-dispatch once with the contract restated and escalate on the second miss.
3. Pin a reviewer that is a DIFFERENT roster member than the builder (the lead is valid) with `lease_pin_reviewer <task> <reviewer>`, review the collected output, then `lease_merge <task> <reviewer>`: ONE squash commit per task on the sprint integration branch, from the lead's own snapshot, never from the branch name. `lease_merge` REFUSES self-review (AE3), an unknown reviewer identity, or a merge with no pin (the pin is the record that a review happened: pin, review, then merge). A protected snapshot (base to snapshot, checked at every merge) also needs a merge approval for that snapshot, the lead's or the user's: `lease_approve task:<task> <lead CLI|user>`; the user's when the lead's own CLI built it (rc 42 without). Findings re-dispatch the same lease/builder with the same pinned reviewer while the cycle is below 3; cycle 3 escalates to the user.
4. At wave end, `integration-verifier` runs against the integration branch, then the lead promotes to the main branch with `lease_promote`. It reads `[promotion] require_user_approval` (default false) and scans the integration diff, BLOCKING (no merge) when approval is required or a protected path is touched. Protected-path diffs (permission configs, deny rules, `ops/roster.toml`, shipped agent configs) force the gate on and require the lead or the user as reviewer, never an external-CLI-only review. A blocked promotion proceeds on the user's `lease_approve promotion:<branch> user`, which a later merge or a default-branch move voids. `lease_merge` also refuses to run when the main tree is on the default branch: merges land on the sprint integration branch; promotion is `lease_promote`'s job.

## Attribution

`ops/CHANGELOG.md` rows: the line `lease_attribution <task>` prints (builder, reviewer and class, lead, approval origin, merge commit).

## Integrity

Every lease helper first compares git config, hooks, refs, worktree pointers and the ledger with the baseline in `ops/leases.toml`; a change the lead did not make escalates the open leases and returns rc 44. After the lead or the user changes any of those on purpose, run `lease_rebaseline` before the next lease call.
