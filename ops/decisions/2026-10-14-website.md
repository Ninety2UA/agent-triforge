# The website lives in site/, built from the repo, on Vercel

- Date: 2026-10-14 (plan), 2026-10-15 (build)
- Sprint: the Agent Triforge website, plan `docs/plans/2026-10-14-2342-feat-agent-triforge-website-plan.md` (local, untracked), unit U12
- Decided by: the user (host, generation sources, the two validator edits, GitHub Pages retired without a redirect); the lead (Claude Opus 5.5) built it
- Related: `site/README.md`, `site/src/lib/` (the data modules and the route table), `site/scripts/ignore-build.sh`, `.github/workflows/gates.yml` (job `site`), `scripts/validate-versions.sh` (the sweep exclusion)

## Decision

The website at https://agent-triforge.dbenger.com is a static Astro site whose source lives in this repository under `site/`, with its own `package.json`. It replaces the single GitHub Pages page `docs/index.html`, which is deleted after the new site is verified; old `ninety2ua.github.io/agent-triforge` links stop working.

Vercel hosts it (project `agent-triforge`, root directory `site`). Deploys come only from a clean worktree of a pushed commit until the repository is connected, and then from pushes to `main`; `site/scripts/ignore-build.sh` skips a build only when none of its inputs changed.

The skill pages, the personas page, the docs and guide pages, the FAQ, the install commands, the changelog, the version and every count are generated from the repo's own files at build time: `skills/*/SKILL.md`, `personas/` and `personas/manifest.toml`, the `docs/*.md` topic pages listed in `DOC_PAGES`, `README.md`, `docs/releases/*.md`, `.claude-plugin/plugin.json`, `templates/ops/roster.toml` and the CLI registry in `scripts/lib/registry.sh`. The home page, page intros, the leases guide and the tutorials are hand-written, and the build checks every skill name they mention against `skills/`. A lead skill also needs one line in `site/src/data/groups.mjs`; without it the build fails and names the skill.

`site/` is not plugin content for the version-bump rule. A change under `site/` changes no installed behaviour, so it needs no version bump and no release, as `docs/` changes do not. The plugin download still includes `site/` (the marketplace source is the repository root), which is why its media stay under a fixed budget.

Two maintainer gates changed with it:

- `scripts/validate-versions.sh` checks 2, 4 and 9 skip `site/dist`, `site/.astro` and `.vercel`, the local build output, so a validator run after a site build passes (fixtures `sweep-site-build-ignored` and its control).
- `.github/workflows/gates.yml` has a `site` job that type-checks, builds and tests the site on every pull request.

The cutover pull request later retargets checks 5, 9 and 11 and their fixtures away from `docs/index.html`.

## Why

The old page drifted from the product: its version badge, several counts and its description of the CLIs no longer matched the repo, and nothing checked them. Generating the pages from the files the plugin ships keeps them true, and the build fails on a broken promise instead of publishing it.

Keeping the source in this repository keeps one pull request for a skill and its page, at the cost of a larger plugin download. A separate repository would have needed its own copy or a fetch of the repo at build time.

The validator edits change only maintainer gates, not plugin behaviour. PR #43 already changed `validate-versions.sh` in a docs-only pull request without a release.

Without the CI job, a plugin pull request that breaks the site build can merge (`main` has no branch protection). Vercel would then keep serving the last good build, and production would stop updating without anyone noticing.

## Revisit when

The plugin download grows past what users accept, or a second site needs the same data. Either would argue for moving `site/` to its own repository and fetching the repo's files at build time.
