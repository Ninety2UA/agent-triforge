## Fixes

### 1. Quote `${CLAUDE_PLUGIN_ROOT}` in hook commands (D-039)

Since Claude Code 2.1.281, `claude plugin validate` warns on an unquoted `${CLAUDE_PLUGIN_ROOT}` in shell-form hooks, and `--strict` turns warnings into errors. All four commands in `hooks/hooks.json` (lines 9, 20, 24, 35) have it. Quote the placeholder (`bash "${CLAUDE_PLUGIN_ROOT}/hooks/handlers/<name>.sh"`) or switch to exec form. Pick one form and use it for all four.

The `plugin-dev` plugin is installed at local scope in this repo. Its `hook-development` skill and `plugin-validator` agent cover this.

### 2. Make probe CC-06 validate both manifests (D-039)

CC-06 reported PASS while the gate was red: `scripts/probe-capabilities.sh` (around line 1528) runs `claude plugin validate --strict "$REPO_ROOT"`, which resolves to the marketplace manifest only. Validate `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` separately, and PASS only when both do, matching release checklist item 1. Keep the existing row ID, name and evidence style.

Never edit the probe harness while a probe run is in progress. Check `pgrep -f probe-capabilities` first.

### 3. Refuse OpenCode V2 (D-049)

OpenCode V2 (npm `@opencode/cli`, shipped 2026-09-11, same `opencode` binary) does not read `OPENCODE_PERMISSION`, so Triforge's deny set is silently dropped. It also defaults to a shared background service that ignores the caller's `env -i` environment. Anyone on V2 runs unconfined today.

Refuse deterministically when the `opencode --version` major is 2 or higher, in both places:
- `invoke_opencode` in `scripts/lib/opencode.sh`;
- the lease `opencode)` arm in `scripts/lib/lease.sh` (around lines 605–619).

The error names the V1 pin (`npm i -g opencode-ai@1`) and fails the way the helper already fails an unusable CLI: match the existing failure classes (the KTD-9 classifier in `scripts/lib/common.sh`) rather than inventing a new exit code. `/setup`'s OpenCode detection reports V2 as unsupported instead of offering enrollment.

Porting to V2 is out of scope (D-049 defers it). Never suggest the npm package `opencode2`: it's a third-party decoy.

### 4. Fix Cursor model ids for Grok 4.7 (D-050)

Grok 4.7 ids have no `cursor-` prefix (`grok-4.7-xhigh`), while 4.6 ids do (`cursor-grok-4.6-xhigh`; the probe record's Appendix B has the host catalog). Every composer strips any `cursor-` prefix, then always emits `cursor-<family>-<effort>`, even for an id that already carries a suffix. So probe CUR-12 fails with "Cannot use this model: cursor-grok-4.7-xhigh". There are **three** composers, all using the same regex, and all three must change together:
- `_cursor_model_for_effort` in `scripts/lib/cursor.sh` (dispatch time);
- the Cursor branch of `resolve_role` in `scripts/lib/roster.sh` (around lines 202–206; every dispatch passes through it);
- the Cursor branch of `roster_write_role` in `scripts/lib/roster.sh` (around lines 662–667; write time).

The prefix belongs to the **family**, not to how the user typed it. `grok-4.6` and `cursor-grok-4.6` must both still produce `cursor-grok-4.6-<effort>`, which is today's behavior and matches `.claude/CLAUDE.md` ("the writer composes the suffix from a bare `grok-4.6`"). `grok-4.7` and `cursor-grok-4.7` must both produce `grok-4.7-<effort>`. Decide the prefix per family from one place: a small known-family table, or the host catalog (`cursor-agent --list-models`) when it's cheap and available, with the table as the fallback. Put that one decision in a single helper that all three composers call, so the id format can't drift between them again.

An already-suffixed id keeps its suffix and gets the family's correct prefix (`cursor-grok-4.7-xhigh` → `grok-4.7-xhigh`). Keep the `-fast` variants and non-Grok ids (`composer-2.5`, …) as they work today. **The shipped pin stays `cursor-grok-4.6-xhigh`**; moving it waits until CUR-12 passes on `grok-4.7-xhigh`.

### 5. Positional `$1` in `commands/setup.md` (S28): reproduce first

`commands/setup.md:310` has `local cli=$1` inside a code block. superpowers #2361 reports that Claude Code substitutes positional `$N` tokens in command and skill bodies, even inside code blocks. If that's true, `/setup roles` renders its ROLES column wrong.

Reproduce it first: make a throwaway project command containing a code block with `$1`, invoke it with an argument, and check whether the text the model receives has been substituted. Record the result in the PR description.
- **If it reproduces:** remove positional tokens from `commands/setup.md`'s body, for example by passing the CLI name as a named variable. Grep `commands/` and `skills/` for other `$N` tokens and fix those too.
- **If it doesn't reproduce:** leave the file alone and say so in the PR.
